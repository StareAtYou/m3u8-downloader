# 任务表单与列表滚动修复设计

## 目标

- 单任务添加成功后，清空 M3U8 地址、任务名称和“允许覆盖”选项，保留保存目录，方便连续添加任务。
- 下载任务持续更新进度时，保留用户当前的任务列表滚动位置和选中项，避免列表反复跳回顶部。

## 非目标

- 不改变批量添加流程、任务排序规则、默认保存目录或任务详情布局。
- 不在每次刷新后强制滚动到最新任务，也不改变用户主动选择的任务。

## 方案比较

1. 在 QML 中记录并恢复 `ListView.contentY`：改动较少，但每次模型重置仍会重建委托，可能闪烁，并容易与新增、删除任务时的合法位置校正冲突。
2. 在 `TaskListModel` 中增量更新：任务 ID 和顺序不变时，仅替换内部快照并对实际变化的行发送 `dataChanged`；任务集合发生结构变化时才重置模型。该方案从根因消除无谓重建，滚动、选中状态和性能都更稳定。
3. 对新增、删除和移动也实现完整的逐行差异算法：最精细，但当前任务量和需求不足以抵消复杂度与维护成本。

采用方案 2。

## 行为与数据流

- `Main.qml` 继续只在桥接层报告 `submit` 成功后清理输入，新增清空 `taskNameInput.text`；失败和覆盖确认阶段不清空，以免用户丢失输入。
- `TaskListModel.replace()` 先生成安全快照并比较新旧任务 ID 顺序：
  - ID 顺序不同：使用模型重置，保持现有新增、删除、重排语义。
  - ID 顺序相同：更新内部数据，仅为内容发生变化的连续行区间发出 `dataChanged`，角色覆盖全部任务展示字段；不触发 `countChanged`。
  - 数据完全相同：不发送更新信号。
- QML `ListView` 因进度刷新不再经历模型重置，因此保持 `contentY`；现有详情刷新由模型数据变化和选中索引继续驱动。

## 验证

- 新增 GUI 回归测试：模拟单任务提交成功，验证任务名称被清空；模拟失败，验证输入仍保留。
- 新增模型测试：同一任务 ID 顺序下更新进度时发送 `dataChanged` 而不发送 `modelReset/countChanged`。
- 新增 QML 集成回归测试：长列表滚动到底部后刷新进行中任务，验证 `contentY` 和当前选中项保持不变，同时行内容得到更新。
- 运行 GUI 相关测试、完整 pytest、Ruff 检查与格式检查。
